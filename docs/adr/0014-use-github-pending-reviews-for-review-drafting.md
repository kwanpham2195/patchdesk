# Use GitHub pending reviews for Review drafting

After a maintainer starts a review, the authenticated viewer's GitHub `PENDING` review is the one authoritative editable Review draft. Patchdesk reads, appends to, finishes, and discards that remote pending review; it does not keep a second editable local copy. Before a pending review exists, the inline composer offers the explicit immediate **Comment now** write or **Start a review**, which creates the pending review with the selected inline comment. Once a pending review is confirmed, new inline authoring offers only **Add review comment** against that remote owner.

The workbench header replaces the hidden Review draft dock with one action: **Start a review** when no viewer pending review is confirmed, and **Finish review · N** when one is. The final summary exists only inside the Finish review modal and is sent only on Submit; Patchdesk does not persist a second local summary field. A pending-review read that cannot prove absence is `Unavailable`, never `None`: it disables new-comment actions and offers explicit retry or **Check GitHub again**, which is the only recovery for an uncertain pending-review write. Explicit Refresh remains the sole normal replacement of the represented GitHub snapshot.

Patchdesk persists a typed operation intent before every Start, AddThread, Submit, and Discard write and persists the confirmed receipt before reporting success. A timeout, lost response, or failed post-write persistence becomes `OutcomeUnknown`, locks conflicting actions, and is never retried automatically. Only explicit reconciliation with GitHub resolves it. This keeps one keyed pending-review owner per Review and preserves recovery evidence without a local mirror or offline queue.

This decision supersedes ADR-0002 (local draft carry-forward across revisions), ADR-0004 (persistent shared bottom draft dock), ADR-0006 (every editable Review draft is local until publication), ADR-0008 (seed a local draft from Analysis), and ADR-0010 (local-draft/preview completion actions) only for the Review-drafting surface. Those decisions described the local `ReviewBatch` authority that this decision replaces; they remain historical record elsewhere.

Remote operation contracts (pending-review read, append-thread, discard, submit-after-head-change, and Reply/Resolve/Unresolve behavior) ship only with evidence from the disposable-PR validation spike. Existing persisted `batchContent` is retained, exported, or discarded only through an explicit product-owner decision with tested migration/recovery before any code deletes, clears, replaces, ignores, or transforms it.
