# Choose a validation style by data boundary

Patchdesk validates untrusted data differently depending on where it enters the system, and the choice follows a decision rule rather than a case-by-case preference. Two questions decide the style: does Patchdesk control the schema on both the write and read side, or is it a third party's payload, and should an invalid piece fail the whole record or degrade field by field?

Every raw string or number is first parsed into a branded nominal type at the boundary where it enters, before any further validation — this is the base layer everything else builds on (`src/domain/ids.ts`). Above that base layer, three further styles apply depending on the data's origin:

A payload from a system Patchdesk does not control, where GitHub can add fields Patchdesk does not model and an unrecognized extra field is expected and harmless, uses `v.looseObject` schemas parsed with `v.safeParse`; a validation failure becomes one whole-payload error rather than a partial read (`src/adapters/github/github-adapter.ts`). A durable record Patchdesk fully owns on both the write and read side, where structural drift means the local copy has been corrupted rather than an external shape evolving underneath it, uses `v.strictObject` schemas that fail the whole read closed; recovery then rebuilds from the authoritative source per the ADR "Recover from invalid local data by rebuilding" (`src/adapters/storage/maintainer-inbox-cache-store.ts`). Local, user-editable preference state with no authoritative external source to rebuild from instead validates every field independently with `v.fallback`, and validates array entries per-item rather than rejecting the whole collection, so one corrupted field or one bad saved view never costs the rest of a maintainer's settings (`src/renderer/src/inbox-view-preferences.ts`).

Future validation-boundary questions — "should this be `strictObject` or `looseObject`?" — should be answered by applying this rule rather than re-litigated case by case.
