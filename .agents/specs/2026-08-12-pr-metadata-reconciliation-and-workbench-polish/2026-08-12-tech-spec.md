# PR metadata reconciliation and workbench polish

## Summary

This spec separates same-revision PR metadata reconciliation from explicit code-revision refresh. A confirmed Patchdesk GitHub write should promptly update checks, review decision, merge readiness, methods, and Conversation state. **Refresh** remains an explicit adoption of a changed remote head/patch and remains the only operation that prepares a new represented-review worktree.

It also makes Pierre's file tree inherit Patchdesk light/dark theme and compacts the PR Overview merge action.

Related execution plan: [`../../PLANS/2026-08-12-pr-metadata-reconciliation-and-workbench-polish.md`](../../PLANS/2026-08-12-pr-metadata-reconciliation-and-workbench-polish.md).

## Context / Current State

`ReviewRefreshService.detect()` compares a remote candidate with the persisted represented snapshot, then returns only `{ updatesAvailable }`. Any checks, review, Conversation, or merge-policy difference calls `markDetectedUpdate`, blocks writes, and requires explicit Refresh. `refresh()` creates a candidate snapshot and prepares a new session only when its head changes.

`ReviewWorkbenchFlow` runs detection after mount, focus/visibility, and every 90 seconds. Confirmed write paths journal their own writes to avoid false stale detection, but do not project changed merge readiness. `MergeConfirmationDialog` uses a stacked selector and full-width trigger. `PierreFileTree` delegates its canvas colors to Pierre defaults, which remain dark in an otherwise light app.

## Goals

- Reconcile safe same-revision PR metadata after confirmed Patchdesk writes and normal observation.
- Expose Refresh only for a remote head/patch change.
- Preserve immutable represented-review worktrees, drafts, Insights, write gating, and uncertain-write recovery.
- Make the changed-files tree follow Patchdesk light/dark theme.
- Make the ready-to-merge action compact and responsive.

## Non-Goals

- Auto-adopting code, downloading a new worktree, or refreshing Insights.
- GitHub writes, retries, credential changes, polling while hidden, or changing the 90-second cadence.
- A new tree library/theme preference or a new merge confirmation policy.

## Invariants

```ts
type RevisionRefresh = "explicit";
type MetadataReconciliation = "automatic";

// Metadata reconciliation may never change these fields.
type RevisionImmutableFields = {
  readonly sessionId: ReviewSessionId;
  readonly headSha: GitSha;
  readonly patchHash: ContentHash;
  readonly worktree: RepresentedReviewWorktree;
};

// A changed revision is never projected as current metadata.
type Observation =
  | { readonly _tag: "RevisionChanged"; readonly detectedAt: IsoTimestamp }
  | { readonly _tag: "MetadataReconciled"; readonly projection: ReviewWorkbenchProjection }
  | { readonly _tag: "Unchanged"; readonly detectedAt: IsoTimestamp };
```

- Only `RevisionChanged` sets `updates_available` and revokes write authority.
- `MetadataReconciled` is allowed only after two reads prove the remote head still equals the represented head.
- Failed and `OutcomeUnknown` writes schedule no reconciliation.
- Renderer accepts a reconciliation projection only when its Review/session/head/patch identity matches its current workbench.

## Design Constraints

- ADR-0001 is superseded only for metadata-only remote activity; ADR-0017 records that decision.
- The main process owns GitHub calls and parses external responses. Renderer receives bounded projections, never raw errors.
- The existing review-level serialization in `ReviewRefreshService` owns refresh and reconciliation ordering.
- Tests use injected GitHub reader/store seams, not module mocks or live GitHub writes.

## Alternatives Considered

### Option 1: Keep all remote activity behind Refresh

Retain `DetectionResult { updatesAvailable }`. This has no new contracts but forces a Refresh after the maintainer's own confirmed approval. It does not meet the requested merge-readiness behavior.

### Option 2: Renderer-side metadata reads

Let `ReviewWorkbenchFlow` call GitHub or compose metadata from write receipts. This weakens the sandbox/main-process boundary, duplicates GitHub mapping, and cannot safely cover checks or remote review policy. Rejected.

### Option 3: Main-process same-revision reconciliation (recommended)

Extend `ReviewRefreshService` with a typed observation result. It fetches and validates a bounded same-head snapshot, persists it as the represented remote snapshot without creating a session, then returns the normal projection. A changed head is terminal for the operation and becomes `RevisionChanged`. This centralizes identity checks, locking, persistence, and projection.

## Recommendation

Adopt Option 3. Keep `refresh()` as the full explicit operation. Replace `detect()` with `observe()` (or retain `detect` as the public name while changing its result) so all automatic activity has one service-owned classifier.

## Proposed Design

### Domain Model and Types

Add to `src/services/review-refresh-service.ts` or a focused `review-observation.ts` Domain/Service contract:

```ts
export type ReviewObservation =
  | { readonly _tag: "RevisionChanged"; readonly detectedAt: IsoTimestamp }
  | {
      readonly _tag: "MetadataReconciled";
      readonly detectedAt: IsoTimestamp;
      readonly projection: ReviewWorkbenchProjection;
    }
  | { readonly _tag: "Unchanged"; readonly detectedAt: IsoTimestamp };

export type ObserveReviewInput = {
  readonly profileId: WorkspaceProfileId;
  readonly reviewId: ReviewId;
  readonly source: "periodic" | "focus" | "confirmed_write";
  // Used only for ordinary detection fingerprint normalization.
  readonly recentWrites?: ReadonlyArray<RecentReviewWrite>;
};

export type MetadataSnapshot = Pick<ReviewRemoteSnapshot,
  "pullRequest" | "comments" | "checks" | "publishedFeedback" |
  "mergePolicy" | "mergeEvidence">;
```

`MetadataSnapshot` deliberately omits `commits`: changing commits is a revision concern. The service reconstructs a complete `ReviewRemoteSnapshot` by taking `commits` from the represented snapshot only after same-head validation.

### Types, Interfaces, and APIs

```ts
class ReviewRefreshService {
  observe(input: ObserveReviewInput): Promise<Result<ReviewObservation, ReviewRefreshFailure>>;
  refresh(input: RefreshReviewInput): Promise<Result<ReviewWorkbenchProjection, ReviewRefreshFailure>>;
}

// existing protected request, changed response DTO
type ObserveReviewResponse =
  | { readonly kind: "revision_changed"; readonly detectedAt: string }
  | { readonly kind: "metadata_reconciled"; readonly detectedAt: string; readonly workbench: WorkbenchResponse }
  | { readonly kind: "unchanged"; readonly detectedAt: string };
```

No new renderer-to-main privileges are required. The existing `POST /v1/reviews/detect-updates` body gains an optional bounded `source` only if the service needs it for observability; it must not accept a renderer claim that a GitHub write succeeded. Prefer local Flow scheduling after its existing confirmed response parser rather than trusting new request data.

### Seams, Boundaries, Adapters, and Implementations

- `GitHubReader`: existing `getPullRequest`, comments, checks, published feedback, and merge policy calls provide `MetadataSnapshot` inputs.
- `ReviewRemoteStore`: saves the verified same-head snapshot candidate.
- `ReviewStore` / `moveReviewToSession`: updates `representedRemote.snapshotHash` and metadata timestamp while retaining the same `sessionId` and `headSha`; reject any other mutation.
- `ReviewWorkbenchProjectionService`: projects the new represented snapshot through its normal main-process path.
- `local-api.ts` parses strict DTOs and projects `ReviewObservation` to `ObserveReviewResponse`.
- `ReviewWorkbenchFlow`: owns coalesced scheduling and stale-response rejection; it cannot synthesize metadata.
- `PierreFileTree`: receives only theme variables/color-scheme from its immediate container.

## Call Stacks and Data Flow

### Current / Old Flow

```txt
renderer interval/focus
  -> POST detect-updates
  -> ReviewRefreshService.detect
  -> GitHub candidate + snapshot fingerprint
  -> metadata difference => markDetectedUpdate
  -> { updatesAvailable: true }
  -> renderer patches revision.freshness
  -> maintainer clicks Refresh
```

### Proposed / New Flow: confirmed approval

```txt
approved GitHub write response
  -> existing write service confirms receipt
  -> ReviewWorkbenchFlow.enqueueObservation("confirmed_write")
  -> POST detect-updates
  -> local-api parse ObserveReviewInput
  -> ReviewRefreshService.observe (review lock)
  -> getPullRequest (head must equal represented head)
  -> parallel bounded metadata readers
  -> getPullRequest again (same head required)
  -> save complete same-head candidate snapshot
  -> moveReviewToSession(same sessionId, same headSha, new snapshotHash)
  -> ReviewWorkbenchProjectionService.project
  -> MetadataReconciled(projection)
  -> local-api DTO
  -> renderer identity check
  -> replace/patch current workbench metadata
```

### Proposed / New Flow: new commit

```txt
observe
  -> getPullRequest
  -> remote head !== represented head
  -> markDetectedUpdate + revoke publication authorization
  -> RevisionChanged
  -> renderer shows Updates available / Refresh
  -> explicit Refresh only
  -> existing ReviewRefreshService.refresh
  -> prepare new represented-review worktree + complete snapshot + projection
```

### Failure, Retry, Cancellation, and Idempotency Flow

```txt
GitHub/storage failure -> err({ reason: "github_read" | "storage" })
  -> local API safe unavailable response
  -> renderer preserves current workbench; no freshness downgrade claimed

confirmed-write observation coalesced while one is running
  -> one pending observation flag
  -> run once more after the active operation settles

write failure / OutcomeUnknown
  -> no enqueue
  -> existing recovery UI remains authority
```

`observe()` reuses the review lock, so it cannot race `refresh()`. Saving the same snapshot repeatedly is idempotent at the content-addressed remote store; `moveReviewToSession` must reject a changed session/head rather than silently overwrite it.

### Observability Flow

Record only safe phase/category fields through `ReviewDiagnosticService`: `metadata_observation`, `revision_changed`, `github_read`, or `storage`. Do not log GitHub payloads, paths, or raw errors. Include profile/review/session identifiers through established diagnostics fields.

## Risks and Open Questions

- Confirm whether the existing remote snapshot hash is intentionally a strict immutable revision artifact. If so, persist metadata separately rather than updating `representedRemote.snapshotHash`; do not decide this without inspecting storage/migration callers.
- Confirm which write services emit a confirmed result versus a merely accepted request; only the former may enqueue observation.
- Pierre's supported color-scheme API must be verified from installed package source/docs before choosing CSS variables.
- Full browser failures must be baselined before treating them as unrelated; focused browser proof remains mandatory.
